# 报告体例

一次 report run 只做一件事：把当前目录 `snapshot.json` 里的事实写成一份能直接交给客户的报告。
不做测试、不联网、不改 `evidence/`，也不写 `snapshot.json` 之外的事实。

## 一、产物与篇幅

只写这三个，不建其他文件、不建目录：

| 文件 | 内容 | 篇幅 |
| --- | --- | --- |
| `findings.json` | 机器可读结论；每条可报告事实（`vuln` / `cred`，不含 rejected）一个对象 | 条数与可报告事实数一致 |
| `index.md` | 给人读的正文 | 固定 6 节；≤3500 字（表格、代码块不计） |
| `findings/<fact>.md` | 每条 `confirmed` 一页 | 固定 6 节；≤2000 字 |

`report.json` / `snapshot.json` / `evidence/` 只读不写。结论少就写短，不凑字数；结论多也不合并、不省略行。只用当前目录里的材料，不读上级目录（case 的 `in_*/` 等）来补结论——报告里的事实必须来自 `snapshot.json`。

## 二、index.md：固定六节

标题逐字照抄、编号不变；不增、不减、不换序、不合并。某一节没有内容时保留标题并写"本轮无…"，不删节。

```markdown
# <主目标域名> 安全测试报告

> 报告编号 <report.json 的 id> ｜ 生成时间 <report.json 的 created_at> ｜ 结论 N 条（已复核 X，待复核 Y）

## 1. 概览
## 2. 结论清单
## 3. 已复核结论
## 4. 待复核结论
## 5. 范围与限制
## 6. 修复建议
```

- 一级标题只有一个；系统名取 `snapshot.json` 的主目标域名，不编客户公司名。
- 标题下只有上面那一行元信息；不写其他抬头、目录、YAML front matter、免责声明。
- 时间只写报告生成时间（`report.json` 的 `created_at`，写成 `YYYY-MM-DD HH:MM`），不编测试起止时间。

下面逐节说写法；每节标题就是上表的 `## N. …`，不要另起层级。

**1. 概览**

- 3–5 条，每条一行：授权范围，结论总数与分布（已复核几条、待复核几条、集中在哪些目标），最该先处理的一两条。
- 只写事实层面的判断；不写"整体安全状况良好/较差"这类没有对应事实的评价，不展开细节。

**2. 结论清单**

- 一张表，列固定：`编号 | 结论 | 位置 | 复核状态 | 详情`；每条 `findings.json` 一行，顺序与 `findings.json` 一致（`confirmed` 在前、`candidate` 在后）。
- `编号` = fact id；`结论` = `findings.json` 的 `title`，不重写；`位置` = `location`。
- `复核状态` 只写 `已复核 confirmed` 或 `待复核 candidate`。
- `详情`：`confirmed` 写 `[findings/<fact>.md](findings/<fact>.md)`；`candidate` 写 `见 §4`。

**3. 已复核结论**

- 每条 `confirmed` 一个 `### 3.<n> <fact> <title>`，按 §2 的顺序编号。
- 每条两段、合计 4–8 行：一段是结论与影响，一段是关键证据（哪个证据文件、看到了什么）；末行写 `完整复现与证据见 [findings/<fact>.md](findings/<fact>.md)`。
- 不抄复现步骤，不贴报文；细节留给 finding 页。
- 没有 `confirmed` 时写"本轮无已复核结论。"

**4. 待复核结论**

- 有序列表，每条 `candidate` 一项：`**<fact> — <title>**。<已看到什么、证据是哪些文件>；未验证：<该事实 `review` 的 verdict/notes 里的第一句判断>。`
- 未验证理由取复核者的判断（verdict 与 notes 的第一句），不自己另写，也不抄证据细节。
- 每条不超过 4 行；证据路径用相对链接，不贴长报文；没有 `candidate` 时写"本轮无待复核结论。"

**5. 范围与限制**

固定三个子节：

- `### 5.1 授权范围与本轮动作`：表格，列固定 `授权目标 | 本轮动作 | 结果`；只列本轮真正动过、且有事实或证据支撑的目标与动作。没碰过的目标不列表，写进 5.2 一句话。
- `### 5.2 止于何处`：无序列表。写清没测什么、测到哪为止、为什么；每条都必须是客户能据以复核的边界（"未对真实账号做口令尝试""未测写入类接口"），不写"没时间"这类我们的处境。`snapshot.json` 里每条事实的 `refs`（打不开的出处）必须原样写在这里，说明"当时在该地址看到过、现在无法回放"；`rejected` 里的每一条也必须在这里列出，并写清它 `review.notes` 的否定原因（哪一点没成立）。
- `### 5.3 需要客户复核的点`：有序列表；只有客户或开发侧才能确认的问题，每条一句。

**6. 修复建议**

- 有序列表，按优先级从高到低；同根因合并成一条。
- 每条一句问题 + 一句修法，指到接口或组件；不重复证据，不写"建议尽快修复"这类空话。

## 三、findings/<fact>.md：固定六节

只给 `confirmed` 建页，文件名 `<fact>.md`，一个 `confirmed` 一页，不能少。标题下先写三行固定字段，再按序写六节：

```markdown
# <fact> <title>

- 位置：`<location>`
- 复核状态：**confirmed**
- 证据：<每个证据写成 [<证据id>-<原名>](../evidence/<证据id>-<原名>)，顿号分隔>

## 1. 前置条件
## 2. 复现步骤
## 3. 请求与响应片段
## 4. 影响
## 5. 修复建议
## 6. 止于何处
```

- `前置条件`：≤4 条，每条一行；写真正需要的条件（登录态、签名材料、网络位置），不写过程。
- `复现步骤`：有序列表，≤8 步，每步一个动作、一行；命令或报文只给能复现的最小形式。
- `请求与响应片段`：≤3 组；每组 `**说明：**` + 代码块 + 一行 `来源：<证据链接>`；超长片段用 `…` 截断，不贴无关日志。
- `影响`：无序列表，3–5 条；先写已证实的，再写依赖条件的；不写没有证据的推测。
- `修复建议`：有序列表，按优先级；每条可执行、指到位置，不重复 §4。
- `止于何处`：无序列表，≤6 条；这条结论没证到哪、哪些分支没测；不得与 index §5.2 矛盾。
- 正文必须出现这条结论引用的每个证据（相对链接）；出现的每个证据都必须属于这条事实，并在 `findings.json` 的 `evidence` 里。

## 四、findings.json

数组，一条可报告事实一个对象，字段顺序固定：

```json
{"fact":"f_x","verdict":"confirmed","title":"…","location":"…",
 "preconditions":"…","impact":"…","trace":"…","evidence":["evidence/e_x-name"]}
```

- `verdict` 只有两种：`confirmed`（事实在事实意图图里 `status=verified`）与 `candidate`（未复核）。
- `confirmed` 的 location / preconditions / impact / trace / evidence 五项一处不能空；`candidate` 也尽量写全，写不了的就在 `trace` 里说明还差什么。
- `title` ≤40 字，一句话说清"什么问题、什么后果"；§2 与 §3 用同一个 title。
- `trace` 一句话复现路径，分号分隔关键动作；报文放 finding 页，不塞进 JSON。
- `evidence` 只放 `evidence/` 下真实存在、属于这条事实的文件，按重要性排序，路径相对报告根。
- 被 rejected 的事实不在 `snapshot.json` 的 `facts` 里，也不写行；它在 `snapshot.json` 的 `rejected` 里（带 `review.notes`），否定结论写进 §5.2。

## 五、写法与一致性

- 简体中文、陈述句、一句一个事实；不用"综上所述""值得注意的是""建议尽快修复"这类空话；不用 emoji、不用 HTML、不写 YAML front matter。
- 标题层级：`#` 只用于标题；小节 `## N. `，子节 `### N.M `；不跳级，不用 `#` 当小节。
- 表格只出现在 §2 与 §5.1；必须有 `| --- |` 分隔行；单元格不换行。
- 代码块必须标语言（`json` / `http` / `bash` / `text`），每组 ≤20 行。
- 证据一律相对链接：`index.md` 里写 `[<文件>](evidence/<文件>)`，finding 页里写 `[<文件>](../evidence/<文件>)`；禁止绝对路径。`refs` 里的 URL 只能作为文字写进 §5.2，不能当证据。
- 同一条事实只在固定位置出现：`confirmed` = §2 一行 + §3 一节 + 自己页；`candidate` = §2 一行 + §4 一项；不在别处重复。
- 所有计数、编号、标题与 `findings.json` 一致；改一处要全局一致。
- 校验不过的报告状态是 `incomplete`，缺什么会在 `checks.json` 里点名——宁可短，不要空、不要编。
